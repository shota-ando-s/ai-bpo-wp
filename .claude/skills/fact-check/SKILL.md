# AIO・LLMO ファクトチェック

対象: $ARGUMENTS

AI に段落単位で切り出され、hikitsugi.jp の名前付きで引用されても誤りにならない記事にする。判定基準と理由は [references/aio-factcheck-rules.md](references/aio-factcheck-rules.md) にある。**検証を始める前に必ず読む。**

`--auto` が付いているとき（seo-article から呼ばれたとき）は、ステップ5で確認を取らずに修正まで進める。付いていなければ、レポートを出して修正方法をユーザーに聞く。

---

## ステップ1: 対象の確認と機械抽出

`$ARGUMENTS` にファイルがなければ、対象の記事を聞く。

```bash
python3 .claude/skills/fact-check/scripts/extract_claims.py articles/<file>.md --check-links --site
```

このスクリプトは次を出す。

- 検証すべき主張の一覧（ID・行番号・種類・出典リンク）。★ は AI が単独で引用しやすい位置（定義文・見出し直後の段落・表・FAQ回答）
- 外部リンクの一覧とリンク切れ。ドメインから一次情報かどうかの目安
- 他の記事で同じ用語を定義している文
- 機械点検の ERROR / WARN（出典のない数値、時点のない数値、最上級表現、指示語で始まる段落、旧ブランド名、「要出典」、excerpt にだけある数値）

スクリプトが拾うのは候補だけ。記事を Read で通読し、スクリプトが拾っていない主張（因果関係、固有名詞、サービスの説明、「〜が多い」「〜が一般的」といった数値のない一般化）も追加する。

## ステップ2: 検証の優先順位を決める

主張を次の順に並べる。上ほど厳しく、確実に検証する。

1. ★ の位置にある数値・制度・料金・定義
2. excerpt とタイトルに含まれる主張
3. 補助金・法律・料金など、時期で答えが変わる主張（rules の「鮮度」の表）
4. 自社（ヒキツギAI・株式会社ふえん）に関する主張
5. その他の数値・固有名詞・因果関係

計算式（時給 × 時間 など）は Web で調べず、自分で計算し直して合っているか確認する。前提条件が書かれているかも見る。

## ステップ3: 並行検証（Agent ツールで2〜3エージェントを同時起動）

主張を分量が均等になるように分け、Agent ツールで **1つのメッセージで同時に** 起動する。補助金・法律・制度の主張が多い場合は、それだけを1エージェントに割り当てる。

各エージェントには次をそのまま渡す（主張は ID・原文・行番号・付いている出典URLをセットで渡す）。

```
次の主張を、一次情報で検証してください。WebSearch と WebFetch を使ってください。

検証の手順:
1. 主張に出典URLが付いていれば、WebFetch でそのページを開き、記事の数値・調査名・時点がページに書かれているか確認する。書かれていなければ「出典不一致」とする
2. 出典が二次情報（まとめ記事・ニュース記事・ブログ）なら、原典（官公庁・調査会社のプレスリリース・報告書・公募要領・e-Gov 法令検索・公式料金ページ）を探す
3. 新しい版（新年度の公募要領、新しい調査、料金改定、法改正）がないか探す。今日は <今日の日付>
4. 主張が単独で引用されても正しいか（対象・条件・時点が文中にあるか）も見る

判定（1つ選ぶ）:
- ✅ 確認済み: 一次情報で裏付けが取れ、引用耐性もある
- 🔧 引用耐性不足: 内容は正しいが、対象・条件・時点・出典が文中に欠けている
- ⚠️ 要注意: 古い／出典が二次情報／細部が不正確／断定が強すぎる
- ❌ 誤り: 一次情報と明確に違う
- ❓ 確認不能: 裏付けが見つからない

主張ごとに次の形で返してください:
ID: / 判定: / 原典URL: / 原典の記述（数値・時点をそのまま引用）: / 修正案（判定が✅以外のとき、そのまま本文に貼れる一文）:

推測で ✅ にしないこと。原典のページを開いて数値を確認できたものだけ ✅ にする。
```

エージェントを待つ間に、自分で次の2つを確認する。

**自社に関する主張**（rules の5）: ブランド名・会社名・監修者の表記、架空の事例・実績・提携先・顧客の声がないか、試算に「当社試算」と前提条件があるか。サービスの説明は `articles/` のサービス紹介記事（`grep -l "ヒキツギAI" articles/*.md`）と食い違っていないか。

**サイト内の一貫性**（rules の6）: ステップ1の「他記事の同じ用語の定義」に加え、記事内の主要な数値（補助金の上限・補助率・締切、統計値）を他の記事で grep し、食い違いを探す。

```bash
grep -n "<数値や制度名>" articles/*.md
```

## ステップ4: レポート

エージェントの結果と自分の確認を統合し、次の形で提示する。

```
## ファクトチェック: <記事タイトル>
ファイル: articles/<file>.md ／ 検証した主張 N件

### サマリー
✅ 確認済み N ／ 🔧 引用耐性不足 N ／ ⚠️ 要注意 N ／ ❌ 誤り N ／ ❓ 確認不能 N
機械点検: ERROR N ／ WARN N ／ リンク切れ N
サイト内の食い違い: N件（他記事 N本）

### ❌ 誤り
**<ID> L<行> <主張の要約>** ★
- 記事: 「<原文>」
- 原典: 「<原典の記述>」<URL>
- 修正案: 「<そのまま貼れる文>」

### ❓ 確認不能 → 削除
### ⚠️ 要注意
### 🔧 引用耐性不足
（各項目は ❌ と同じ形）

### 自社に関する主張
### サイト内の食い違い
- <用語・数値>: この記事「…」／ <他記事ファイル> 「…」→ 正: <原典URL>

### ✅ 確認済み
<ID と要約を1行ずつ>
```

★（引用されやすい位置）の項目は各区分の先頭に並べる。

## ステップ5: 修正方法の確認

`--auto` のときはこのステップを飛ばし、「すべて修正」として進める。

それ以外は AskUserQuestion で聞く。
- **すべて修正**: ❌ ⚠️ 🔧 ❓ をすべて修正する（推奨）
- **誤りと確認不能だけ修正**: ❌ と ❓ だけ修正する
- **修正案の提示のみ**: ファイルは変えない
- **修正しない**

サイト内の食い違いで他の記事も直す必要がある場合は、どの記事を直すかも同じ質問で聞く（`--auto` のときは他の記事は直さず、レポートに残す）。

## ステップ6: 修正

1. 修正前に `cp articles/<file>.md articles/<file>.md.bak` でバックアップを作る
2. rules の「判定と修正の方針」に従って直す
   - ❌ → 原典の内容に書き換え、出典リンクを同じ文に付ける
   - ⚠️ → 最新の一次情報に差し替え、時点を書く。断定は根拠の範囲まで弱める
   - 🔧 → 対象・条件・時点・出典を同じ文に足す。表は直前の一文か表の中に出典と時点を書く
   - ❓ → 削除する。「要出典」「〜とも言われる」で残さない。削除して文脈が切れる場合は前後の文をつなぎ直す
3. excerpt に修正した数値が含まれていれば、excerpt も直す
4. 削除で FAQ が7問を下回ったり、H2 が空になったりしたら、確認済みの情報で補うか構成を詰める

修正後に次の2つを通す。

```bash
python3 .claude/skills/fact-check/scripts/extract_claims.py articles/<file>.md --check-links
python3 .claude/skills/seo-article/scripts/check_article.py articles/<file>.md
```

- extract_claims.py の ERROR が0になるまで直す。残す WARN は理由を控える
- check_article.py の ERROR も0にする（削除で内部リンク数や文字数が基準を割ることがある）

## ステップ7: 結果の報告

```
修正 N件（❌ N ／ ⚠️ N ／ 🔧 N ／ ❓削除 N）
主な修正: <2〜3件、変更前 → 変更後>
残した WARN: <理由>
他の記事で要修正: <ファイルと内容。直していなければ明記>
```

`--auto` のときはここで呼び出し元（seo-article のステップ7）に戻る。

単独で実行したときは「投稿しますか？」と聞く。承認されたら投稿し、`.bak` を削除する。既存記事の更新なので画像は再生成しない（`--rebuild-images` を付けない）。

```bash
python3 post.py articles/<file>.md
rm articles/<file>.md.bak
```

投稿前に、frontmatter の slug が本番の slug と一致しているか確認する（一致しないと重複記事ができる）。コミット・デプロイはユーザーに頼まれたときだけ行う。
