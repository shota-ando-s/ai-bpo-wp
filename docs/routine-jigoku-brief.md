## 1. 位置づけ：SNS漫画と記事の役割分担

「ルーティン地獄」は、既存の SNS 漫画シリーズ「引き継ぎ地獄」と並ぶ新シリーズとして検討されている。この企画書は、そのうち **kantan-ai.jp に載せる記事** を扱う。

| 媒体 | 役割 | 解決策を出すか |
|---|---|---|
| SNS 漫画・X スレッド・縦書きカルーセル | 「これ、うちの会社でもある」と共感させ、余韻を残す | 出さない（毎回出す必要はない） |

## 4. 連載の主張（全記事で守る）

漫画企画の「最も重要な判断基準」を、記事でもそのまま背骨にする。

> ルーティン地獄とは、誰も望んでいない業務が組織の中で当たり前になり、続いてしまう状態のこと。
> 「無駄だと全員わかっているのに、誰も変えられない」。それは担当者の能力や根性の問題ではなく、構造の問題である。

記事で守ること:

- **誰も悪者にしない。** 担当者も上司も誠実に仕事をしているのに、不合理な状態が続く。その構造を書く。「やり方が古い」「ITに弱い」とは書かない。
- **精神論や個人の能力に帰結させない。**
- **AIで全部が解決するとは書かない。** 毎回「人が決めること」を明記する。
- **自動化の前に「やめられないか」を問う。** 目的を失った業務を自動化すると、無駄が速く回るだけになる。これを連載の誠実さとして差別化にする。

## 5. ルーティン地獄の2つの型

業務を「続ける理由があるか」で2つに分ける。記事ではどちらの型かを最初に示す。

### 型A：続ける理由がなくなった業務 → まず、やめる・減らす

漫画企画のエピソードの多くがこの型に入る。

- 誰も活用しない月次報告書を作り続ける
- 誰も読まない日報を書き続ける
- 前任者から引き継いだ仕事の目的を、誰も説明できない
- 業務をなくすための検討会議が、新たな定例業務になる

この型でのAIの役割は、作業の代行ではなく **やめる判断の材料づくり**（誰が読んでいるか・何に使われているかの棚卸し、やめた場合の影響の洗い出し）にとどまる。

### 型B：必要だが、道具が途中で止まって手作業が残る業務 → AIと分担する

既存ツール（Excel、RPA、OCR、SaaS）が止まる場所は4つに集約できる。2026-11-07 に公開事例・公的資料22件を整理して得た分類。

| 止まる場所 | 何が起きているか | 代表的な業務 |
|---|---|---|
| 形式バラバラ地獄 | 書類の形式が取引先ごとに違い、読み取り後の修正や取引先ごとの保守が残る | FAX注文書、受領した請求書、領収書 |
| 例外地獄 | ルールで処理できない例外が混ざり、そこだけ人に戻ってくる | 入金消込（部分入金・合算入金）、経費の規程外申請 |
| あと出し変更地獄 | 確定したあとに変更が入り、組み直しが発生する | シフトの再調整、日程のリスケ |
| 確認・聞き直し地獄 | 別の人・別の場所への確認や聞き取りが要る | 営業からの「注文届いてる？」、介護記録の聞き取り、見積の単価確認 |

### なぜ誰も変えられないのか（両方の型に共通）

ハブ記事で扱う。次の4つは漫画企画のエピソードから読み取った **当社の仮説** で、調査で確かめたものではない。

- 目的を知る人がいない（引き継ぎのたびに理由が抜け落ちる）
- やめてよいと決める人が分からない
- 確認しようにも、確認する相手がいない
- やめて何か起きたときの責任を、誰も負えない

1つ目は「引き継ぎ地獄」とつながる。かんたんAIの本業（業務の引き継ぎ）への自然な導線になる。

### 作業の種類（ニーズ調査の仮説）

ニーズ調査では、現場の自動化ニーズを「転記をなくしたい」「確認をなくしたい」「定型作業をなくしたい」の3つに分けている。これは **作業の種類** の軸で、上の「止まる場所」（なぜ手作業が残るか）とは別の軸として併用する。記事のタグに使う。ニーズ調査自身が「定性的な仮説であり、件数による検証は未実施」としている点に注意する。

## 6. 連載の構成

```
ハブ記事: ルーティン地獄とは（2つの型、誰も変えられない理由、連載の主張）
  ├── 型A：やめる・減らす → 誰も読まない日報、使われない報告書、目的不明の引き継ぎ業務…
  └── 型B：AIと分担する
        ├── 形式バラバラ地獄 → FAX注文書、受領請求書、領収書…
        ├── 例外地獄 → 入金消込、経費精算…
        ├── あと出し変更地獄 → シフト再調整、日程調整…
        └── 確認・聞き直し地獄 → 社内照会、介護記録…
```

- 業務別の記事は冒頭でハブ記事へリンクし、ハブ記事は全業務記事へリンクする。
- 分類ごとの一覧ページは、記事が3本以上たまってから作るか決める。

## 7. 記事の型（業務別記事）

seo-article の「本文の型」に、連載の構成を当てはめる。見出しは検索クエリの形にする。

| H2（例：Excel転記） | 書くこと |
|---|---|
| リード | 地獄の情景（毎朝の何分、誰が、何をしているか）と、この記事の答えの要旨 |
| Excelの転記がなくならないのはなぜ？ | 実際の声の要約（出典つき）。一文目で答える |
| その転記は、まだ必要？ | 型Aのチェック：誰が使っているか、やめたら何が困るか |
| これまでの解決策で何が楽になった？ | 関数・マクロ・RPAなど、AI以前の解決策と効果 |
| それでも人の手に残る作業は？ | なぜ機械で止まるのか。4つの止まる場所のどれか |
| AIに任せられるのはどこまで？ | 分担表（AIがやる／人が確認する／人が決める） |
| 経営者が見るべき数字は？ | 月何時間・誰の時間か。試算は「当社試算」と前提条件を書く |
| 小さく始めるなら何から？ | 最初の1歩と注意点（誤処理、個人情報、承認の設計） |
| よくある質問 | 7問。`## よくある質問` ＋ `### 質問？` の形 |
| まとめ | 要点3〜5個と、無料業務診断への導線 |

型Aの業務（日報・報告書など）の記事では、「AIに任せられるのはどこまで？」を「やめる・減らす判断はどうする？」に置き換える。

分担表の形（全記事で共通にする）:

| 作業 | AIがやる | 人が確認する | 人が決める |
|---|---|---|---|
| 例：元のシートから値を拾って転記先に入れる | ○ | | |
| 例：形式が変わった元データの読み替え | 候補を出す | ○ | |
| 例：その転記を続けるかどうか | 使われ方の棚卸し | | ○ |

## 9. 現場の声・事例の扱い

ニーズ調査の調査要件を、記事でもそのまま守る。

- **原文で確認できない内容は、事実として書かない。** 投稿の URL と投稿日を控え、記事に書く前に実在と内容を確かめる。ニーズ調査に載っている URL は前回の調査で集めたもので、まだ確かめていない。
- **紹介記事と当事者の投稿を区別する。** ベンダーの導入事例は「事例」、担当者自身の不満・相談・体験談は「現場の声」と書き分ける。連載では現場の声を優先する。
- **推測で補完しない。** 頻度などが投稿から分からなければ書かない。
- **確認された事実と、当社の仮説・提案を分けて書く。** 「AIならこう分担できる」は事例ではなく当社の考えなので、「当社の考え」「想定例」と分かる書き方にする。
- 投稿は要約し、匿名化する。SNS の投稿は転載しない。引用するなら短く1件までにし、個人が特定できる情報は書かない。
- **架空の事例・実績・提携を書かない**（`memory/project_brand_name.md`）。ふえん自身の実績は、事実として確認できるものだけ書く。
- 数値には出典と時点を付ける。自社試算は「当社試算」と前提条件を書く。
