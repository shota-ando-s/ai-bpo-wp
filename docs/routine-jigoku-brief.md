## 1. 位置づけ：SNS漫画と記事の役割分担

「ルーティン地獄」は、既存の SNS 漫画シリーズ「引き継ぎ地獄」と並ぶ新シリーズとして検討されている。この企画書は、そのうち **kantan-ai.jp に載せる記事** を扱う。

| 媒体 | 役割 | 解決策を出すか |
|---|---|---|
| SNS 漫画・X スレッド・縦書きカルーセル | 「これ、うちの会社でもある」と共感させ、余韻を残す | 出さない（毎回出す必要はない） |
| LinkedIn | 業務改善の構造的な問題をビジネス視点で考察する | 考え方まで |
| kantan-ai.jp の記事（本企画） | 具体的な業務の場面を描き、「AIでやるとこうなる」を手順で示す | 出す |

漫画で共感した人が「では、どうすればいいか」を知りたくなったときの受け皿が記事になる。漫画の回と記事のテーマをそろえ、漫画から記事へリンクする。

## 3. 読者

| 読者 | 状況 | 記事で届けたいこと |
|---|---|---|
| 中小企業の経営者 | 現場の手作業に、誰の時間が月何時間かかっているか見えていない | 作業の見える化と、やめる・任せるの判断基準 |

## 4. 連載の主張（全記事で守る）

> ルーティン地獄とは、毎日・毎月くり返す業務を、**だましだまし続けている状態** のこと。
> 1回は数分で済み、慣れた人がやれば回り、小さな工夫で延命できる。だから誰も止めない。けれど、時間とミスの種は毎日たまっていく。
> 引き継ぎ、急な休み、繁忙期、制度の変更は、その地獄が **表に出る日** にすぎない。地獄はその日に始まるのではなく、ずっと続いている。

漫画企画の「無駄だと全員わかっているのに、誰も変えられない」も、この「だましだまし」の一つの姿として扱う。

記事で守ること:

- **誰も悪者にしない。** 担当者も上司も誠実に仕事をしているのに、だましだましの状態が続く。その仕組みを書く。「やり方が古い」「ITに弱い」とは書かない。
- **精神論や個人の能力に帰結させない。**
- **AIで全部が解決するとは書かない。** 毎回「人が決めること」を明記する。
- **自動化の前に「やめられないか」を問う。** 目的を失った業務を自動化すると、無駄が速く回るだけになる。

### だましだましが続く仕組み（当社の見立て）

ハブ記事で扱う。調査で確かめたものではなく、当社の見立てとして書く。

| 続く理由 | よくある姿 |
|---|---|
| 1回が短い | 「5分で終わるから」と、月に何時間になるかを誰も足し算しない |
| 慣れた人なら回る | ベテランがやればミスなく終わるので、困っていることが見えない |
| 小さな工夫で延命できる | セルの色分け、付箋、手書きメモ、自作マクロで、仕組みを変えずに乗り切る |
| 変える判断をする人がいない | 現場は「変えていい」と言われておらず、経営者は作業の中身を知らない |

## 5. 地獄が表に出る日（露見のきっかけ）

だましだましの業務は、ふだんは回っている。次のようなきっかけで、急に回らなくなる。記事では「この業務は、どの日に表に出るか」を1つ書く。

| きっかけ | 何が起きるか |
|---|---|
| 担当者の急な休み・退職・異動 | 手順が頭の中にしかなく、誰もできない |
| 繁忙期・件数の急増 | 1件5分が積み上がり、残業でも終わらない |
| 取引先・制度の変更 | 形式が変わり、延命の工夫が効かなくなる（インボイス制度、電子帳簿保存法など） |
| ミスの発覚・監査 | 目視の確認が抜けていたことが分かる |
| 人を採用・育成しようとしたとき | 手順を説明できず、教えられない |

引き継ぎは、このきっかけの一つとして扱う。連載の中心には置かない。

## 6. ルーティン地獄の9つの型

だましだましの業務を、作業の性質で9つに分ける。1つの業務が複数の型にまたがることはある。記事では一番効いている型を主な型にする。

ユースケースは、業種と業務を特定した「よくある例」。各記事は、この粒度の場面を1つ選んで書く。

| 型 | どんな作業か | ユースケースの例（業種・業務） | AIでやるとこうなる（要旨） |
|---|---|---|---|
| 転記地獄 | 同じ情報を、何か所にも打ち直す | 工務店の事務。見積Excelの金額を、発注書・工程表・請求書に毎回手で打ち直す | 見積から各書類の下書きをAIが作り、人は差分だけ確認する |
| 突き合わせ地獄 | 2つの数字を目で照らし合わせる | 卸売業の経理。月末に銀行明細と請求一覧を並べ、カナ略称の振込名義を取引先に当てて入金消込 | 一致する入金はAIが消し込み、名義違い・合算・差額だけが理由つきで人に届く |
| 集計地獄 | バラバラに届く数字を、毎日・毎月まとめる | 飲食店5店舗の本部。毎朝、各店からLINEやメールで届く売上報告をExcelにまとめる | AIが各店の報告を読んで集計表に入れ、いつもと違う数字に理由の候補をつける |
| 催促地獄 | 人を追いかけて、集める・待つ | 中小製造業の経理。月末、各部署の経費精算と取引先の請求書がそろわず、メールと電話で催促する | 期日と未提出者をAIが管理し、相手に合わせた催促を送る。人は期限を延ばすかどうかを決める |
| 例外地獄 | ルールに乗らない「ちょっと違う」を人が裁く | 通販のカスタマー対応。期限切れ・開封済み・セットの一部など、規約にぴったり当てはまらない返品の申し出を判断する | AIが規約と過去の対応から判断案と返信の下書きを作り、人が決めて送る |
| 読み取り地獄 | 紙・FAX・写真・PDFを読んで入力する | 食品卸の受注担当。飲食店からFAX・手書き・LINEの写真で届く注文を、販売管理に入力する | AIが形式を問わず読み取って登録し、品番や数量が怪しい行だけ人が確かめる |
| 組み直し地獄 | 決めたあとの変更で、全部組み直す | デイサービスの管理者。利用者の急な欠席や職員の休みで、毎朝の送迎表とシフトを組み直す | AIが条件を満たす組み替え案を出し、人が選んで確定する |
| 誰も読まない地獄 | 目的を失った報告・日報・会議を続ける | 不動産管理会社の営業部。毎週月曜に全員が週報を出し、課長がまとめて部長に送るが、誰も読んでいない | AIは作業を代行しない。誰がいつ読んでいるかの棚卸しを手伝い、やめるかどうかは人が決める |
| 秘伝のExcel地獄 | 作った人しか分からない仕組みで回っている | 部品メーカーの生産管理。10年前に誰かが作ったマクロ付きExcelで生産計画を立てている。壊れたら誰も直せない | AIがマクロと数式を読み解いて手順書にし、作り直すか残すかの判断材料をそろえる |

### 作業の種類（ニーズ調査の仮説）との関係

ニーズ調査は、現場の自動化ニーズを「転記をなくしたい」「確認をなくしたい」「定型作業をなくしたい」の3つに分けている。9つの型との対応は次のとおり。ニーズ調査自身が「定性的な仮説であり、件数による検証は未実施」としている点に注意する。

| ニーズ調査の分類 | 対応する型 |
|---|---|
| 転記をなくしたい | 転記地獄、読み取り地獄 |
| 確認をなくしたい | 突き合わせ地獄、催促地獄、例外地獄 |
| 定型作業をなくしたい | 集計地獄、誰も読まない地獄 |
| （対応なし） | 組み直し地獄、秘伝のExcel地獄 |

## 8. 事例の書き方：抽象化しない

**事例は「業種・人物・時刻・手順」まで具体的に書く。** 「経理の照合作業」ではなく、「従業員30人の食品卸で、経理担当が毎月25日、銀行のネットバンキングから明細をCSVで落とし、請求一覧のExcelと横に並べて1行ずつ色を塗っていく」と書く。そのうえで、同じ場面をAIでやると手順がどう変わるかを、Before と After で並べる。

Before / After の書き方（例：突き合わせ地獄 × 卸売業の入金消込）:

| 手順 | Before（今のやり方） | After（AIでやると） | 人がやること |
|---|---|---|---|
| 明細を集める | ネットバンキングからCSVを落とす | 毎朝、AIが明細を取り込む | — |
| 照らし合わせる | 請求一覧と並べて1行ずつ目で照合し、色を塗る | 金額と名義が一致する入金をAIが消し込む | — |
| 名義が違う入金 | 「カ）ヤマダシヨウテン」が誰かを記憶で当てる | 過去の照合結果から取引先の候補を出す | 候補を確認する |
| 合算・差額 | 電卓で組み合わせを探し、分からなければ営業に聞く | 組み合わせの候補と、差額の理由（振込手数料など）を出す | どれで消し込むか決める |
| 取引先への確認 | 電話かメールを書く | 確認メールの下書きを作る | 送るかどうか決める |

## 9. 記事の型（業務別記事）

seo-article の「本文の型」に、連載の構成を当てはめる。見出しは検索クエリの形にする。

| H2（例：入金消込） | 書くこと |
|---|---|
| リード | 場面の描写（業種・人物・時刻・作業）と、この記事の答えの要旨 |
| 入金消込が手作業で終わらないのはなぜ？ | 具体的な場面と、だましだましの工夫（色塗り、記憶、電卓）。一文目で答える |
| その作業は、まだ必要？ | やめる・減らす余地のチェック |
| この地獄が表に出るのはどんな日？ | 5章のきっかけのうち、この業務で起きやすいもの |
| AIでやると、手順はどう変わる？ | Before / After の表（8章の形） |
| AIに任せず、人が決めることは？ | 判断・承認・取引先とのやり取りなど |
| 経営者が見るべき数字は？ | 月何時間・誰の時間か。「当社試算」と前提条件を書く |
| 小さく始めるなら何から？ | 最初の1歩と注意点（誤処理、個人情報、承認の設計） |
| よくある質問 | 7問。`## よくある質問` ＋ `### 質問？` の形 |
| まとめ | 要点3〜5個と、無料業務診断への導線 |

誰も読まない地獄の記事では、「AIでやると、手順はどう変わる？」を「やめるかどうかは、どう決める？」に置き換える。

## 11. 事例・現場の声の扱い

### 想定例（よくある例）

- **嘘でなければ、架空の場面でよい。** 多くの中小企業で起きている、あるあるの業務を、業種・人物・時刻・手順まで具体的に描く。
- 本文では「よくある例」「想定例」と分かるように書く。実在の会社やお客さまの事例のように書かない。
- **ふえんの実績・お客さまの数・導入効果を作らない**（`memory/project_brand_name.md` の「架空の事例・実績・提携を書かない」はこの意味）。ふえん自身の実績は、事実として確認できるものだけ書く。
- 想定例の中の時間や件数は「想定」とし、当社試算として前提条件を書く。
- 場面は、実際によくある姿から外れないようにする。あり得ない手順や、極端に盛った数字は書かない。

### 統計・公開事例・現場の投稿

- 統計や制度は一次情報にリンクし、時点を書く。
- **原文で確認できない内容は、事実として書かない。** 投稿の URL と投稿日を控え、記事に書く前に実在と内容を確かめる。ニーズ調査に載っている URL は前回の調査で集めたもので、まだ確かめていない。
- **紹介記事と当事者の投稿を区別する。** ベンダーの導入事例は「事例」、担当者自身の不満・相談・体験談は「現場の声」と書き分ける。
- 投稿は要約し、匿名化する。SNS の投稿は転載しない。引用するなら短く1件までにし、個人が特定できる情報は書かない。
